# Async Web-Size ZIP Queue — Design Spec ("Tier 3, web-size")

**Status:** Draft — scoping only, not yet started
**Author:** Nick Porterfield + Claude
**Date:** August 23, 2026
**Builds on:** docs/tier3-async-zip-queue-spec.md (the hi-res async queue, shipped v1.5.7) — same underlying problem, same proven infrastructure patterns, different image-processing step

---

## 1. Problem statement

Web-size ZIP downloads have the same large-gallery problem the hi-res async queue (v1.5.7) was built to solve — entirely client-side, sequential per-image fetches, tab must stay open the whole time.

Current flow (`downloadZipClientSide` in `clientApi.js`, and a near-identical loop in `GalleryDetail.jsx`'s `doPhotographerZipDownload`):
- Browser fetches each image individually from `GET /download/:key?size=web`
- Paced at 650ms apart (Worker's 100 req/min/IP rate limit on `/download/`)
- Each response accumulated into a `JSZip` archive in browser memory
- Whole ZIP built client-side, then triggered as a browser download

For 200 images, that's 2+ minutes minimum just from pacing, before any actual transfer time. Tab must stay open the entire time — no resilience to closing it, no "email me when it's ready."

**Worse than hi-res in one way:** web-size downloads aren't gated by `allow_hires_download` at all — any client can trigger this, so it may get hit at scale even more often than hi-res was before v1.5.7.

## 2. What's already true, confirmed in code (Aug 23, 2026)

These aren't assumptions — verified by reading the actual handlers tonight.

### 2a. Most images already have a pre-generated web-size file — the "fast path"

`r2-worker/src/handlers/download.js`, single-image `GET /download/:key?size=web`:
```js
// --- WEB: serve pre-generated JPEG directly if available (fast path) ---
if (size === 'web' && webKey) {
  const webObj = await env.BUCKET.get(decodedWebKey)
  if (webObj) { /* just stream it back, no processing at all */ }
}
```
`gallery_images.web_r2_key` is populated at upload time (per README: "web-size JPEG (generated at upload time, served directly)"). For the common case, resolving a web-size image is just a plain R2 read — **identical in shape to the hi-res fetch step already built for the Tier 3 Workflow.**

### 2b. WASM resize+watermark is a fallback, not the common case

Same handler, when `web_r2_key` is missing:
```js
// --- WEB: resize + watermark + JPEG (fallback for images without web_r2_key) ---
const wmConfig = watermarkId ? await fetchWatermarkById(watermarkId, env) : null
jpegBytes = await processWebImage(inputBytes, wmConfig)
```
`processWebImage` lives in `r2-worker/src/utils/imageProcess.js`, built on `@cf-wasm/photon/workerd` (`resize`, `watermark` from that package). This is the only piece of real new capability the Workflow would need — and it's only needed for images that don't already have a `web_r2_key`.

### 2c. A server-side streaming ZIP endpoint for size=web already exists — and isn't used by the frontend

`r2-worker/src/handlers/zip.js`, `POST /download-zip` with `size: 'web'`, already:
- Streams the ZIP progressively via a `TransformStream` (never holds the whole archive in memory — same memory-safety property the async Workflow needs)
- Builds real ZIP entries per image, same byte-level format helpers as everywhere else in this codebase

**But it always calls `processWebImage` on the raw original for every single image** — it does NOT check for a pre-generated `web_r2_key` first, unlike the single-image handler. So today, this endpoint does full WASM resize+watermark work for every image, every time, even when a pre-generated file already exists. That's a real inefficiency in existing code, independent of anything built tonight — worth fixing regardless of what else happens with this spec (cheap, low-risk fix: check `webKey` first, matching `download.js`'s existing fast-path pattern, before falling back to `processWebImage`).

**Open question for tomorrow, first thing:** why doesn't the frontend already call this endpoint for web-size ZIPs, the same way it calls the hi-res sync endpoint for small hi-res ZIPs? Two live theories, need to confirm which (or if both matter):
- **CPU-time theory:** Cloudflare Workers have a per-invocation CPU-time limit separate from wall-clock duration. WASM resize+watermark is CPU-bound. Doing many of these sequentially within *one* Worker invocation (even while streaming output) could hit that limit for a large gallery — which the current client-side loop avoids by spreading each image's processing across a separate Worker invocation. If true, this matters a lot for how the async Workflow should be built (see section 3).
- **Historical theory:** this endpoint may have been built after the client-side loop was already shipped, and nobody switched the frontend over. Check git blame / commit dates on `zip.js`'s `size=web` path vs. `downloadZipClientSide`'s pacing comments to see which came first.

If it's purely historical and CPU-time isn't actually a real constraint at realistic gallery sizes, the sync-fallback tier (small galleries, under whatever threshold gets chosen) might not need any new code at all — just point the frontend at the existing `/download-zip?size=web` endpoint instead of the client-side loop, after fixing the fast-path gap in 2c. That would only leave the *async* tier for genuinely large galleries as real new work.

## 3. What this means for the Workflow design

If the CPU-time theory holds, the Workflow's per-image step should mirror the hi-res pattern exactly:

```
fetch-image-N step:
  1. Check for web_r2_key -- if present, plain R2 get (fast path, matches 2a)
  2. If absent, fetch original + fetchWatermarkById + processWebImage (fallback, matches 2b)
  3. Write result bytes straight to an R2 scratch key -- same confirmed-safe
     pattern as hi-res (Workflow step OUTPUTS are capped at 1MiB; never
     return image bytes from a step)
  4. Return only small metadata (scratchKey, size, crc, name)
```

This keeps each image's CPU-bound work inside its own step/invocation, same as the hi-res queue already does per-image R2 reads. The `build-and-upload-zip` step (fixed-size byte splitter, R2 multipart upload) should be almost entirely reusable as-is from the hi-res Workflow — it doesn't care what produced the bytes, only that they're sitting in scratch keys.

**Reusable, already proven infrastructure from the hi-res build (v1.5.7) — should not need to be re-derived or re-tested from scratch:**
- Scratch-key pattern for keeping step outputs under the 1MiB cap
- Fixed-size (8MiB) byte splitter for R2 multipart — confirmed via both a standalone simulation and a real 160-image gallery that R2 requires exact equal part sizes, not just "≥5MiB"
- `zip_jobs` table, RLS, and the two notification Edge Functions (`send-zip-ready-email` / `send-zip-failed-email`) — likely reusable as-is or with a small `download_kind` / `size` column added to distinguish hi-res jobs from web-size jobs, rather than a whole new table
- Cloudflare Workers Paid plan already active (1000 subrequest limit, not 50) — no action needed, already done
- The `GET /zip-jobs/:id` / `GET /zip-jobs/:id/download` endpoints and the `/download/:jobId` frontend page — likely reusable as-is if web-size jobs go into the same `zip_jobs` table

## 4. Open questions to decide before building

1. **Answer the section 2c question first** — CPU-time constraint or historical accident? This determines whether the sync tier needs any new backend work at all, or just a frontend endpoint swap plus the small fast-path fix.
2. **Sync/async threshold** — own decision, not necessarily the same 25 images / 250MB as hi-res. Web-size files are typically much smaller than originals, so the byte threshold in particular may want to be different; the image-count threshold might also differ if CPU-time-per-image (not transfer size) turns out to be the real constraint.
3. **Shared `zip_jobs` table vs. a separate table** — leaning toward shared with a `download_kind` column (`'hires'` / `'web'`), given the schema is otherwise identical, but worth a deliberate decision rather than a default.
4. **Fix the section 2c fast-path gap in `zip.js` regardless** — cheap, low-risk, benefits any gallery still using the sync path after this ships, independent of the rest of this spec.

## 5. Testing plan (learn from the hi-res build)

The hi-res spike's 2-image test validated the *mechanism* but missed two real bugs that only appeared at real scale (a 160-image gallery hit a memory limit, then an R2 multipart equal-part-length constraint neither of which showed up small). Same discipline applies here:

- Test the fast path and the WASM fallback path separately, each against a real gallery big enough to matter (not just 2-3 images)
- If the CPU-time theory is confirmed, specifically test a gallery with enough images that WASM processing time would meaningfully add up, to make sure per-step CPU limits are respected
- Don't consider this done until it's been run against a real large gallery and the resulting ZIP has been downloaded and opened, same bar as v1.5.7
