# FinalVault v1.6.0 — Invoicing System Scope

Status: **Scoped, not yet migrated.** This document is the output of the dedicated scoping session called for in the v1.6.0 note. No SQL should be written from this without a final read-through — see Open Questions at the bottom.

**Visual reference**: `v1.6.0-ui-mockups.html` (same folder) is a single consolidated page with all 8 screens mocked during this session — Financials dashboard, Session Detail invoice card, session wizard's invoice step, the invoice editor in both its editable and payment-locked states, the payment schedule, the catalog manager, and the Client Portal invoices view. Open it in a browser for the full visual picture; layout/content reference only, not pixel-accurate to real components.

## Goals

Replace the flat `session_fee` / `retainer_amount` / `retainer_paid` / `balance_due` / `balance_due_date` / `payment_status` fields on `sessions` with a real, standalone Invoice system: itemized or flat invoices, a flexible payment log instead of a two-stage retainer/balance toggle, and client-facing visibility in the Portal. No real payment processing (no Stripe Connect) — manual payment recording only, plus a link to the photographer's existing payment platform (Venmo/PayPal/Ko-Fi/Cash App/Zelle).

## Data model

### `invoices`
- `id`, `photographer_id`
- `session_id` — **nullable** FK to `sessions`. Nullable supports standalone invoices (print sales, licensing, anything with no session). One-to-many: a session can have any number of invoices (retainer, final balance, later add-ons like reprints) — no join table, no multi-session invoices (explicitly ruled out).
- `client_id` — FK to `clients` (who it's billed to; usually derivable from session but needed directly for standalone invoices)
- `invoice_number` — sequential integer, scoped per photographer, no year prefix (matches QuickBooks' default behavior — plain auto-increment, no reset per year). Starts at **1001** (cosmetic — avoids a client's first invoice reading as "#1" or "#9").
- `status` — lifecycle enum: `draft`, `sent`, `void`
- `due_date` — nullable
- `payment_platform` — snapshot of the platform key used at send time (one of the `payment_links` keys), overridable per invoice, defaults from `photographers.default_invoice_platform`
- `notes` — freeform, shown to client
- `tax_rate` — nullable percent, off by default. Applied only to line items marked `taxable`.
- `discount_rate` — nullable percent, off by default. Applied proportionally across all line items before tax.
- `created_at`, `sent_at`, `updated_at`

### `invoice_line_items`
- `id`, `invoice_id`
- `catalog_item_id` — nullable FK to `invoice_catalog_items` (null for pure freeform lines)
- `title` — short name (e.g. "Full Wedding Package")
- `description` — optional longer text (e.g. "10-Hour Wedding Package. Includes Primary and Secondary Shooter...")
- `quantity`, `unit_price`, `unit_label` (nullable, snapshotted from the catalog item at time of add so later catalog edits don't retroactively change past invoices — editable per line)
- `taxable` — boolean, default `true`, inherited from the catalog item's `taxable_default` when picked, editable per line
- `sort_order`
- Every invoice is built from line items — even a "quick" flat-amount invoice is just one line item under the hood. This keeps the schema single-shaped instead of branching between a "simple" and "itemized" invoice type. The UI can still offer a one-field "quick invoice" entry mode that creates a single line item behind the scenes, so this doesn't add friction for the common case.

### `invoice_catalog_items`
- `id`, `photographer_id`, `name`, `description`, `default_unit_price`, `unit_label` (nullable, e.g. "mi", "hr", "session" — shown as "$0.65 / mi"; blank means flat-price, no unit shown), `taxable_default` (boolean, default `true`), `active` (boolean, default `true`)
- Reusable service/product catalog (e.g. "8x10 Reprint — $25", "Engagement Session — $350"). Picking one pre-fills a line item (title, description, price, unit, taxable); the line item's own fields can still be edited per-invoice without touching the catalog record.
- **Delete vs. archive**: a catalog item that has never been used on an invoice (`invoice_line_items.catalog_item_id` reference count = 0) can be hard-deleted. One that's been used on at least one invoice can only be archived (`active = false`) — hard-deleting it would orphan the FK on real, already-issued invoices. Archived items are hidden from the picker by default but stay in the catalog manager behind a "Show archived" filter, with a Restore action to bring one back to `active = true`.
- **Default seed catalog** for new accounts (fully editable/deletable, generic across photography niches — not deliverable-specific since that varies too much by business type):
  - **Session Fee** — Covers the photographer's time, talent, and equipment for the scheduled session or event.
  - **Retainer / Deposit** — A non-refundable deposit paid to reserve the photographer's date and time. Applied toward the total balance due.
  - **Travel Fee** — Covers mileage, transportation, and time spent traveling to and from the shoot location.
  - **Editing / Retouching** — Post-production work including color correction, exposure adjustment, and standard retouching on delivered images.
  - **Rush Editing / Delivery** — Expedited turnaround on final edited images, ahead of the standard delivery timeline.
  - **Additional Hour** — Extra coverage time beyond what was included in the original session or package.
  - **Second Shooter / Assistant** — An additional photographer or assistant present to provide extra coverage angles or support during the shoot.
  - **Location / Venue Fee** — A fee charged by the shoot location or venue, passed through to the client.
  - **Print Release / Usage License** — Grants the client rights to print and reproduce their images for personal or specified commercial use.
  - **Reshoot Fee** — Covers a follow-up session scheduled to redo or supplement a previous shoot.
  - **Late Booking Fee** — Applied when a session is booked within a short window of the requested date.
  - **Cancellation / Rescheduling Fee** — Applied when a booked session is cancelled or rescheduled outside the agreed notice period.
  - Validated against general photography-invoicing practice (session/creative fee, licensing, travel, retouching, deposits all appear consistently as standard categories) — this list deliberately excludes deliverable-specific items (prints, albums, digital gallery formats) since those vary too much by niche to seed usefully.

### `invoice_payment_schedule`
- `id`, `invoice_id`, `sequence` (1, 2, 3...), `amount`, `due_date`
- Optional — splits the invoice total into planned installments (e.g. 50% at booking, 50% before the shoot), matching the "Payment Schedule" pattern from the reference screenshot (amount + auto-computed % + due date per row, "Add another payment").
- **Functionally tied to actual payments**, not just informational: `invoice_payments` rows apply against schedule entries in order — payments fill installment 1 until it's covered, then installment 2, etc. Each schedule row's status (`Unpaid`/`Partial`/`Paid`) is computed the same way the invoice's overall status is, just scoped to that row's cumulative allocation.
- When no schedule exists, payments just apply against the invoice total directly (today's simple case).
- **Editing behavior**: changing one row's amount auto-rebalances the other unpaid rows so the schedule always sums to the invoice total — no manual "fix the other row" step, no window where the schedule visibly doesn't add up.
- **Lock-once-paid**: a row that shows `Paid` becomes read-only (amount/due date), same principle as a `Sent` invoice's line items locking — the client already paid against those numbers, so retroactively editing them would misrepresent what happened. Unpaid/partial rows stay fully editable.

### `invoice_payments`
- `id`, `invoice_id`, `amount`, `paid_date`, `method` (freeform text or small enum: cash/check/venmo/paypal/other), `note`
- Flexible log — any number of manual payments against an invoice, logged whenever. Replaces the retainer/balance two-stage toggle entirely.

### `photographers` (new column)
- `default_invoice_platform` — one of the existing `payment_links` keys, used to pre-fill new invoices

## Computed values (never stored, always derived)

- **Subtotal** = `sum(line_items.quantity * unit_price)`
- **Discount amount** = `subtotal * discount_rate` (0 if `discount_rate` is null)
- **Taxable subtotal** = `sum(quantity * unit_price)` for line items where `taxable = true`, less its proportional share of the discount
- **Tax amount** = `taxable_subtotal (post-discount) * tax_rate` (0 if `tax_rate` is null)
- **Total** = `subtotal - discount_amount + tax_amount`
- **Amount paid** = `sum(invoice_payments.amount)` for the invoice
- **Balance due** = `total - amount paid`
- **Payment status** (display-only, computed): `Unpaid` (paid = 0) → `Partial` (0 < paid < total) → `Paid` (paid >= total). If a payment schedule exists, each schedule row gets its own status computed the same way, scoped to payments allocated to it in order.
- **Overdue** — a flag, not a state: `due_date` (or, if a schedule exists, the next unpaid installment's `due_date`) has passed AND payment status ≠ Paid. Shown as a badge layered on top of Unpaid/Partial, not its own status value.

This fixes a real soft spot in the current model, where "retainer paid" is a checkbox a person has to remember to click — payment status now always reflects what's actually been logged.

## Payment link generation

The Portal's "Pay via [Platform]" button doesn't just link to the photographer's static payment page — it pre-fills the amount due and a note (invoice number) where the platform supports it, so the client doesn't have to type anything:

| Platform | Pre-fill support | Link format |
|---|---|---|
| Venmo | Amount + note | `venmo.com/{username}?txn=pay&amount={balance_due}&note=Invoice+%23{invoice_number}` |
| PayPal (PayPal.me) | Amount only | `paypal.me/{username}/{balance_due}` |
| Cash App | Amount + note | `cash.app/${cashtag}/{balance_due}` (or their official Payment Links flow, which also supports both — needs confirming which mechanism to build against at implementation time) |
| Ko-fi | Unconfirmed | Plain link only, no pre-fill, until verified |
| Zelle | **None** — Zelle has no shareable payment link at all | Not a clickable button — falls back to displaying the photographer's Zelle email/phone as plain text for the client to enter manually in their own banking app |

This means `payment_platform` handling needs per-platform link-building logic, not one generic template, plus an explicit non-link fallback UI for Zelle (and Ko-fi until confirmed). Balance due and invoice number are computed/read at render time, not stored — the link is generated fresh each time the button renders, not persisted on the invoice.

## Status lifecycle (photographer-controlled)

- **Draft** — not visible to the client
- **Sent** — finalized and visible in the Client Portal
- **Void** — canceled, kept for the record, excluded from outstanding-balance totals and reporting

## Edit lock

Editability is **not** tied to Draft/Sent/Void — it's tied to whether any payment has been logged:

- **No payments logged yet** (regardless of Draft or Sent) — fully editable: line items, amounts, due date, everything. A typo caught after sending doesn't require void-and-reissue as long as the client hasn't paid anything against it yet.
- **At least one `invoice_payments` row exists** — line items, quantities, and prices lock. The client already acted financially based on those numbers, so retroactively changing them would misrepresent what happened. Due date, payment platform, and notes stay editable. Corrections beyond that go through void-and-reissue.
- Same principle applies at the schedule-row level: an unpaid installment stays editable (per the auto-rebalance rule above); a row that's absorbed a payment locks.

## Client-facing behavior

- **Client Portal**: invoices show alongside galleries/contracts/questionnaires — view line items, amount paid, balance due, and the selected payment platform link
- **PDF export**: available both to the photographer and from the Portal (client can download)
- **Email on send**: sending an invoice (draft → sent) triggers a client email, same infrastructure as gallery/contract emails — needs a new template type with variables like `{{invoice_number}}`, `{{invoice_total}}`, `{{balance_due}}`, `{{due_date}}`, `{{portal_link}}`

## Payment reminders

Both a manual and an automatic path, built together:

- **Manual**: a "Send reminder" button on the invoice, available any time it's `sent` and not fully paid. Reuses the invoice-email infrastructure with a reminder-flavored template.
- **Automatic**: new Edge Function + `pg_cron`, same pattern as existing notification jobs. Targets the invoice's `due_date`, or — if a payment schedule exists — the next unpaid installment's `due_date`.
- **Cadence** (fixed for v1.6.0, not user-configurable): 3 days before due, on the due date, then every 7 days while overdue, capped after 3 overdue sends (so a long-unpaid invoice doesn't nag indefinitely).

## Migration — existing session financial data

**Decision reversed from initial scope**: yes, migrate. Checked the live data first (per standing rule — never assume DB layout):

```sql
select id, session_date, session_fee, retainer_amount, retainer_paid,
       balance_due, balance_due_date, payment_status, created_at, updated_at
from sessions
where mode = 'private'
  and (session_fee is not null or retainer_amount is not null or balance_due is not null)
order by session_date desc nulls last;
```

9 rows total. Real data simplified the conversion rules significantly:
- `retainer_amount` is null and `retainer_paid` is false on every row — the retainer feature was never actually used, so there's no retainer/balance split to reconstruct.
- `payment_status` only ever appears as `paid` or `unpaid` — no `partial` cases exist historically.
- One row has `session_fee` null but `balance_due` populated — need a fallback.

**Conversion rules:**
- One invoice per qualifying session, `invoice_number` assigned sequentially starting at 1001 in `session_date` order
- Line item: `description: "Session fee"`, `unit_price: session_fee`, falling back to `balance_due` if `session_fee` is null
- `payment_status: paid` → invoice `status: sent` + one `invoice_payments` row for the full amount
- `payment_status: unpaid` → invoice `status: draft`, no payment row (never had a real invoice conversation with the client historically, so don't auto-send)
- `paid_date` on migrated payments = session's `updated_at` (no real payment-date field ever existed in the old schema) — `note` field flags it explicitly: *"Migrated from legacy session financials — payment date approximated from session's last update."*
- `due_date` = `balance_due_date` as-is (null stays null)
- Old `session_fee`/`retainer_amount`/etc. columns stay on `sessions` untouched (historical record), just no longer read by the UI going forward

## Explicitly out of scope for v1.6.0

- Stripe Connect or any real payment processing — link-out to existing manual payment platforms only
- Invoices spanning multiple sessions (ruled out as a tracking nightmare)
